## 蓝牙交接

主应用原先在 `BluetoothA2dpSink.connect` 隐藏 API 检查失败后保留 A2DP，同时继续申请音乐焦点，触发原车蓝牙向 iPhone 发送暂停。现在该失败可以转入组件 10 的会话租约：

- 主应用和组件双向核对固定包名／证书、当前用户、组件 10 的系统共享 UID、实际蓝牙权限及服务状态；每次请求核对调用 UID、版本、配对手机和系统限制。仅两个现有 CarPlay 包可调用。
- 只能临时抑制这次 CarPlay 所选 iPhone 的 A2DP sink。确认恢复接口可用后才请求断开，不操作蓝牙总开关、配对、HFP 或 SCO；其他手机及通话状态会阻止连接变更。
- **系统受理不算完成。** 组件和主应用分别查询真实 A2DP 状态；确认断开前，本应用音乐静音且不申请永久音乐焦点。通话／Siri 的 transient 焦点及用户保存的媒体焦点禁用选项保留。
- 租约跟随 CarPlay 会话，而非音乐的每次播放／暂停或焦点波动。取消、断开、退出、主进程 Binder 断开会释放；组件在最后一个持有者释放后，仅恢复自己请求断开的连接。原本已断开的 A2DP 不会被自动连接。
- 更换当前会话时，新旧持有者可以交接同一手机的租约，避免先恢复再断开。通话中有界等待恢复，另一手机接管、配对／身份／策略变化时不抢占。恢复请求接受也不写成已连接。
- 外部重新连接 A2DP 会撤销已确认状态，阻止继续争抢；不每秒反复断开，不循环发 PLAY 抵消暂停，不修改隐藏 API 全局策略。
- USB 不要求开启车机蓝牙或额外配对 iPhone。明确关闭蓝牙、或明确未配对且无需操作该手机 A2DP 时，正常放行 USB 音乐；权限／配对查询失败仍作为未知状态，不伪造交接完成。

直接接口可用时保留原有按手机记录的交接及恢复流程；隐藏接口不可用时由独立组件承担租约。组件未更新、被拒绝或交接超时时，日志明确记录原因，不能继续以音乐焦点掩盖尚未完成的交接。

## 原厂媒体源：先验证助手自身准入

新增独立模块 `media-assistant`，真实包名 `com.shilapi.xcertplay.mediaassistant`，版本 `preface-media-assistant-1 / 1`，使用独立 UID 和同一已核对的公开 AOSP 平台测试证书。主应用包名、原签名和 QQ 资料接入保持原值。授权组件的系统授权职责不混入媒体助手。

助手只声明 OEM 媒体中心权限，没有蓝牙、VPN、app-op、音频焦点、无障碍、通知或设置管理功能，也没有桌面图标。仅使用手写的 compile-only SDK 声明，运行时使用车机的 SDK；不会把厂商实现或声明模块装进 APK。

主应用仍先尝试自己的原厂 SDK。被拒绝／不可用时，才探测已经安装且证书、用户、版本、权限和导出服务均匹配的助手。助手以自己的 Context 和包名执行 SDK 初始化及 `registerMusic`，只有 **真实 SDK ready 且真实注册 token 非空** 才通知主应用可用。

只有有效 CarPlay 播放、已获焦点且没有通话／语音抑制时，主应用才异步请求助手申请播放源。助手再次核对当前会话、调用身份和通话状态，返回原厂 `requestPlay` 的实际布尔结果；成功后按空列表、source=6、真实播放记录发布。播放／暂停、上一曲／下一曲仍是四种独立语义，经当前会话原有 HID 和跨入口去重执行。没有真实歌词输入时保持空歌词。

主应用不等待远程助手阻塞 UI。异步授予或发布迟到时，核对当前 token、请求、资格代际及后端；暂停、失焦、取消、会话替换或关闭后，旧授予不能重新获得音源。助手回调也需通过当前租约、Binder、实际归属、命令资格和音频模式检查。两端的初始化、请求和回复都有边界，拒绝后不按位置更新循环申请。

**平台签名不等于 ECARX license。** 缓存 OpenAPI 服务端中，系统应用标志的快捷准入与普通用户安装的平台签名是不同条件；构建 99 已证明主包 QQ 资料仍被拒绝。本助手没有复制 QQ／Linkco 授权或伪造系统应用标志，也没有修改服务端、注入原厂 Binder、绕过被拒绝 SDK 或冒用其他包名。助手能否在 IHU353G / 系统 169 取得 ready、token、requestPlay，必须由新包实车日志核实；若助手也被拒绝，仍需它自己适用的有效准入资料，不能描述为音源归属已经修复。

## 单 APK 分发与手动安装

主 APK 生成资产任务同时依赖两个独立组件的 Release 构建及签名，已随构建 100 执行并核验嵌入字节：

| 主 APK 内路径 | 内容 |
| --- | --- |
| assets/authorization/authorization.apk、manifest.json | 授权组件 10，系统共享 UID，固定平台证书。 |
| assets/media-assistant/media-assistant.apk、manifest.json | 独立媒体助手 1，独立 UID，固定平台证书。 |

`scripts/media_assistant.py` 复用现有本机签名输入校验，不下载新密钥，不扩大公开凭据白名单。它核对助手包名／版本／marker、API 28、平台证书、独立 UID、最小权限及 DEX 定义；拒绝在助手 APK 中打包厂商 SDK 类、原始签名材料或复制的授权资产。元数据的 `sdkAdmissionVerified=false` 明确表示打包校验不证明实车准入。

授权页仍使用原有同一行的“保存授权 APK”和“打开下载目录”按钮。保存先核验两个嵌入 APK，再分别导出到公共 Download 根目录，并显示各自路径。按用户 2026-10-20 最新要求，导出文件名固定为 `Preface-Android9-Authorization.apk` 和 `Preface-Media-Assistant.apk`，不带版本号；先复制并校验临时文件，再覆盖同名旧文件，不追加编号。两个文件都已存在且内容相同则不重复写入或自动打开目录。已安装的未知／系统同包名助手仍保留，不能降级覆盖。页面只打开目录，用户在文件管理器逐个手动安装，不直接调起 APK 安装器，不自动安装或授权。

只更新主应用不会更新车机上的独立组件。后续实车测试需要用户手动更新授权组件 10、安装媒体助手 1；主 APK 仍使用原证书，可覆盖安装并保留数据。

固定文件名与同名覆盖修改完成后，导出、两个组件校验、导出协调及授权页共 **69 项定向测试通过**，失败、错误、跳过均为 0。覆盖两项组件更新后沿用原路径、不同内容覆盖、相同内容去重及其他文件保留；记录位于本机 `agent_docs/export-fixed-names-20261020/`，本次仍未打包或安装。
