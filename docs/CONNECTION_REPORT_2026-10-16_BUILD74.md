每组附近均为 `musicActive=false`、`focusHeld=false`、`mediaStreamActive=false`；媒体系统音量为 10，导航 11。蓝牙三个 profile 聚合状态为 2，只是连接状态，`playingState=event_only` 与 `oemSelectedSource=unavailable` 无法确认实际 A2DP 播放或原车选源。没有本轮新的 A2DP 播放事件证据。沿用用户之前已确认的手机及车机音源选择，不能重复归因于未选蓝牙音乐。

代码复核：蓝牙模式关闭 CarPlay 音频公告／主音频资源，不申请媒体焦点，媒体转发准入排除该模式。报告没有应用媒体键转发暂停的记录，但这不等于证明原车 AVRCP 或手机路由层没有发起／拒绝播放。`disableBluetooth` 在 496–522 行触发的是无线引导链路交接；`CarPlayController.closeBluetoothBootstrapTransport()` 只关闭本应用 CSM、RFCOMM 流和 socket，没有关闭蓝牙适配器或调用 A2DP/HFP 断开。不能把命令名称直接当成原车蓝牙被应用关闭的证据。

当前实验方案只是撤下 CarPlay 音频能力，并没有替手机建立 A2DP 音频路由；本轮表明这种声明修改还不足以保证这台车机／手机组合正常播放。待对齐每次自动暂停时手机实际输出路由、原车 A2DP 播放事件和 AVRCP 动作，以及 CarPlay `modesChanged` 的音频资源归属。现有日志只记录资源键名，无法确定是谁使播放停止。

原厂媒体中心 SDK 351 仍在注册前返回 `ready=false / api-not-ready`（60–74 行）。服务可解析、导出且无绑定权限要求，不等于该调用者取得了媒体 API 授权或服务 Binder；没有新的拒绝原因证据，不能仅凭 `mediaPermission=false` 确认根因。这也不能直接解释系统原车蓝牙为什么自动暂停。

## USB 阻塞位置与新增证据

1. 12:39:35.417 找到匹配当前 iPhone NCM 的 `usb0`，驱动 `cdc_ncm`、归属／MAC／接口索引匹配、IPv6 地址 ready、carrier=1；12:39:35.481 在 IPv6 7000 监听，公告地址／端口与 bind 一致（732–758 行）。
2. 12:39:35.883 MFi 认证通过，手机报告 wiredAvailable=true；正常路径发出一次 StartSession（770–778、836 行）。这不是认证失败或尚未建立系统网卡。
3. 后续有邻居 reachable、网卡 RX/TX 增长与 IPv6 投递计数增长，轮询的 TCP 表始终只有监听，`synReceived=0 / established=0`；12:40:06.050 超时，StartSession 已等待约 30.1 秒、`tcpAccepted=0`（854–923、929 行）。轮询看不到瞬时状态，不证明正常路径从未收到任何 SYN。
4. 12:40:06.120 起才强制 claim NCM control/data，切换为原始诊断，并再次发送诊断用 StartSession（943–954 行）。15 秒结果收到 10 帧：8 个 IPv6 TCP、2 个 IPv4 DHCP Discover；协议头分类 `synTo7000=8`。这是相较旧报告只有 DHCP 的新增证据：手机在原始诊断阶段确实尝试发往 7000 端口的 TCP 建连（976–980 行）。
5. 三次探针 bulk OUT 均返回 -1，完整接受 0 次、Echo Reply 0、`bidirectionalConfirmed=false`；CDC 链路通知先 down，最终 up（957–982 行）。负返回值没有 errno，不能直接称为明确超时、NAK 或物理 OUT 损坏。GET_NTB_FORMAT 返回 -1、CRC mode 可读，不足以确认所有传输参数（947–950 行）。
6. 原始诊断接管接口后没有应用 TCP/IP 栈，也不是备用 AirPlay 服务。不能期待它响应 SYN 建立 CarPlay；不能将它看到的 SYN、OUT 失败直接倒推成正常内核路径的收发原因。分类器未核对 SYN 的目的 IPv6／MAC 是否命中公告端点，也未验证 TCP 校验和或区分重传，8 是报文计数，不是 8 次独立连接。
7. 12:40:21.418 测试结束后明确 Failed 并停止自动重试；12:40:44.757 控制读出现 DeviceUnavailable，时间晚于前面的 TCP 超时和诊断结束，不能倒作初始失败原因。12:40:49 的主动断开约 35 ms 完成清理（983–1012 行）。

下一轮 USB 取证应先确认 SYN 的目标端点／MAC 与公告匹配，以及正常内核路径的入站 TCP、过滤及回复路径；若系统可见性不足则明确说明，不据无日志认定放行。原始诊断需另核对其传输参数和 OUT 失败原因。保持不用 root／VPN、不将原始诊断充当连接回退；诊断结束后按既有说明重新插拔 USB。
