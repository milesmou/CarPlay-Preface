# 原厂高德红绿灯倒计时升级评估

2026-10-30，用户询问能否将原厂高德升级到支持红绿灯的新版本。按现有上下文，以 2023 款星瑞 E02 的**中控高德显示红绿灯倒计时，同时保留原厂仪表准备和 CarPlay 导航提示**为目标；没有将需求扩展为仪表显示红绿灯倒计时。

**目前没有可交付的、同时保留原厂仪表能力的升级包。** 不能把修改版本号、复制旧仪表库或出现倒计时类名当成功能已启用。本轮仅继续分析，没有修改、重新签名、构建或安装高德，也没有变更 CarPlay 源码／版本或恢复已撤回的独立服务。

## 已核对的两份输入

沿用用户确认使用的 327 固件：AutoMap 5.0.7.605871／6030053，APK SHA-256 `82272e4dc531c3ff1b1c6fff02d5fc0362f963319e435e0f5021d4b6dc5c67dc`。不是实际 169 的 5.0.7.606132。用户提供的 9.5.0.600013／26000001 APK SHA-256 `094e296ef0783a76d3c2a82a2b91a5eb3198cef2338db78549295617f523ed92`。

| 检查 | 事实与边界 |

| 原厂 `libGbl.so` | 实际包含 `GuideTrafficLightLayerItem`、`GuideTrafficLightTimer`，并有包含灯态、倒计时与坐标的日志格式。这是原生处理／绘制的线索，不证明此定制应用能收到实时数据或已经启用界面。 |

## 官方资料及解释

[高德车机版官方下载](https://auto.amap.com/download) 本轮列出 9.5.0，并在 9.1.0 更新记录中列出红绿灯功能升级；这是公众版说明，不能等同于已提供星瑞 E02 的新版原厂定制适配。

[AutoSDK 500 的红绿灯图层文档](https://a.amap.com/amapauto/static/bl/500/android/api/classcom_1_1autonavi_1_1gbl_1_1layer_1_1_guide_traffic_light_layer_item.html) 描述灯态与秒级倒计时。其接口与本机原生层线索一致，但 **AutoSDK 版本标识不等于高德应用版本号**，该文档不是当前原厂包功能已经开通或服务端可用的证明。没有将手机导航 SDK 的开关、授权或版本号直接套到车机定制应用。

## 后续可验证方向

优先核对原厂已有底层能力能否取得真实灯态数据、完成定制界面显示，并保持原厂仪表准备、停止和冷启动行为。若实际缺少这些环节，再评估具有对应数据功能和 E02 适配的新版原厂包，或在新核心上重新适配原厂仪表接口；这属于新核心的兼容工作，不能承诺已具备匹配插件。

当前结论是有值得继续核对的原厂底层线索，尚未建立可运行补丁或保留仪表的完整升级方案。原有“依赖原厂高德准备”的 CarPlay 1213 行为保持不变。

## 修改后能否覆盖安装

随后按用户问题，使用本机 `apksigner` 针对 Android 9／API 28 实际核验两份固定哈希 APK：均通过 v3 签名验证，包名均为 `com.autonavi.amapauto`，证书 SHA-256 均为 `c8a2e9bccf597c2fb6dc66bee293fc13f2fc47ec77bc6b2b0d52c11f51192ab8`。与本机已核对来源的公开 AOSP 平台测试签名输入匹配；仅检查文件哈希，没有输出原始密钥、签名高德或安装应用，也不改变 CarPlay 签名或授权组件。

据此具备制作同包名、同证书覆盖包的签名条件，不能沿用修改前已经失效的 APK 签名，也不能用 CarPlay 证书替代。Android 的更新签名规则见 [官方说明](https://developer.android.com/studio/publish/app-signing#considerations)。新构建号需高于实际安装包；用户 9.5 的 `versionCode` 为 26000001，若当前安装这一版本，修改包必须高于该值。缓存原厂的 6030053 不能直接当作后续覆盖 9.5 的新构建号。

仍未从实车读取实际安装包的证书、APK 哈希或当前版本，不能将 327 证书当成 169 车机已核验。覆盖安装的签名条件不等于新旧数据格式、红绿灯功能或原厂仪表兼容已经验证。核验原文及结构化记录分别位于本机 `stock327-apksigner.txt`、`supplied95-apksigner.txt` 和 `signing-compatibility.json`，均在前述忽略目录中。

## 后续研究与新提供公众版

继续分析时，已成功解读原厂 FuncConfig、UiConfig、PathConfig 与 GblConfig，所读配置未发现明确的红绿灯读秒启用键；不能再将这些文件整体格式未知作为当前结论。原厂引擎还可定位 `TrafficLightProvider` 的实时请求、路径／在线检查、响应时间检查、灯态通知和绘图资源，但尚未确认 E02 定制应用如何实际启用并取得数据，仍没有可运行的读秒补丁。原始内容与本地分析程序只保留于忽略目录，没有修改原始 APK 或替换原生库。

用户随后提供另一份公众版 9.5，并提出向该包迁移仪表作为替代方向，独立结果见 [公众版仪表移植评估](PREFACE_AMAP_PUBLIC95_INSTRUMENT_PORT_2026-10-30.md)。它的原生库与前次改版相同，旧插件的不兼容仍存在；其证书也不同于前文已核对同证书的原厂／改版两包。前文签名结论仅适用于原先两份固定哈希输入，不能泛指所有 9.5。

随后按用户“验证原厂能否收到真实倒计时”及明确打包授权，已制作并安装仅恢复原始代码的 327 模拟器验证包，详见 [运行验证](PREFACE_AMAP_TRAFFIC_LIGHT_RUNTIME_2026-10-30.md)。启动因模拟器缺少 ECARX 系统类而失败，未进入导航请求阶段，原厂接收仍未确定；没有制作功能补丁或实车升级包。新检出的历史 9.5 连续读秒消息单独归属，不作为原厂成功证据。
