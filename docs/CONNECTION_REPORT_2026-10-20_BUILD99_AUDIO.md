# 构建 99：连接后自动暂停、切歌转入蓝牙音源

2026-10-20，分析用户提供的 E 盘应用诊断、车机日志和 APK。实际设备为 **IHU353G / Android 9 API 28 / 系统 169**，主应用 **0.1.1 / 99**。本轮只更新分析记录，没有修改运行代码、构建、签名、安装或运行单元测试。

## 结论

本次已取得原车进程证据：CarPlay 音频已经建立，但原车蓝牙音乐链路仍连接；蓝牙进程在失去／没有音乐焦点时向同一 iPhone 发送 AVRCP 暂停。同一次方控下一曲也被原厂媒体中心处理，原车蓝牙播放器发出 NEXT 和 PLAY 并重新取得音乐焦点，随后本应用失去焦点。两条控制路径相互干扰，解释了连接成功后暂停、切歌后听到蓝牙通道的现象。

同时，原车 OpenAPI **仍明确拒绝本应用的 mediacenter 授权**。已核实构建 99 确实带有用户要求的 QQ 授权文件及配套参数，不能再把文件接入描述为车机已经准入。这与单纯 Android 音乐焦点获准是两项独立结果。

本次无线一次、USB 两次均复现相同的切歌归属冲突；不能将问题限定为 USB、LPCM 或某一次连接。

12:48:36 的前一次 USB 会话也有相同的“本应用获焦点 → 蓝牙 LOSS → AVRCP PAUSE”链路，证据为 main_log_2 第 281901、281950、281957 行。无线会话中，12:46:18.189568 蓝牙记录 audioFocus=0，18.690730 延迟发送 PAUSE；应用 2700 行在 20.056 收到暂停，证据为 main_log_2 第 120739、121613、121617、121621 行。

因此不能用“CarPlay 没拿到焦点”解释连接后的首次暂停。实际情况是本应用拿到 Android 焦点，而仍连接的蓝牙链路把原车的失焦／无焦点转换成对手机的暂停命令；手机上的同一播放器也因此暂停。

源码对照：`BluetoothAudioHandoff.kt:155–185` 在断开前先检查 connect 可用于日后恢复，失败则保留原连接。本次隐藏 API 告警指向 connect，支持交接在恢复能力检查处失败；不能把普通应用的 NoSuchMethodException 写成固件没有此方法。不能简单删掉恢复检查，留下无法恢复的蓝牙连接。现有平台代理仅代办蓝牙模式的 connect，没有接入 CarPlay 模式的断开流程。

## 排查优先级与边界

当前构建 99 的 11 条媒体 AudioTrack 统计均为 writeErrors=0、decoderDroppedTotal=0、rebuffers=0。最后 USB 会话的媒体收包统计无序号缺口，播放头持续推进；无线存在较长到包间隔，但同类冲突也发生在正常的 USB LPCM 链路。没有证据支持把增大缓冲、换 codec、改媒体流或重做 USB/VPN 作为本次两项故障的首要修复。

后续修复需要分别解决：

1. **CarPlay 音频与原车蓝牙的交接失败。** 当前应用在隐藏 API 不可用时继续保留 A2DP，原车仍能发送暂停。应采用实际可用、限定所选手机且能恢复的交接方式，并核对 A2DP 的真实状态；不能用循环给手机发送 PLAY 或反复抢焦点抵消暂停。
2. **本应用真实的原厂媒体源归属。** 需要验证有效的准入方式，使 ready、注册 token、requestPlay 和原车方控目的地均成立。普通焦点获准、本应用按键 sent=true、添加更多去重都不能代替该链路；强行拉回页面也不能修复音源被夺走。

以上是修复方向，没有新增代码或验证成功的替代方案。不能仅因本次身份不匹配，就扩大为第三方授权或原厂媒体方案没有参考价值。构建 98 当时“两种切歌正常”的用户反馈保留为历史事实；本次构建 99 的三次实测证明问题仍然存在，不能继续以此前反馈认定已修复。
