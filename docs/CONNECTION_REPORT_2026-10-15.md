## 播放后自动暂停

多次 iPhone 播放状态的 true → false 间隔为 1505、1127、1462、1121、1122 ms；例如 11:24:52.056 → 53.177、11:25:50.486 → 51.608（行 1848–1852、2054–2056）。11:25:21 → 42 的 20.779 秒播放段另计，不混作同一种一秒暂停。

这些短暂停记录中 `focusHeld=true`，没有对应的负向 Media focus 事件或本应用 PAUSE／PLAY_PAUSE 发送记录。接收／解码统计也没有同期写入错误或丢包证据；iPhone 先报告暂停，音频流随后结束。这与单纯本地 AudioTrack 静音或应用因失焦主动暂停的表现不同。

蓝牙 AVRCP 与 CarPlay 同时控制同一手机仍是合理候选，但日志没有 A2DP 播放状态、AVRCP 命令来源或原厂播放器动作，不能确认该候选。11:24:22.444 的 `disableBluetooth` 在 23.029 完成的是应用 iAP2 RFCOMM bootstrap 向网络隧道交接（行 1746–1773）；代码只关闭自己的 bootstrap transport，不表示车机 A2DP／HFP 已断开。不能据此声称蓝牙媒体竞争已排除。

用户后续补充：音乐自动暂停时，仪表盘出现蓝牙音乐播放标识。这是原车蓝牙音源参与的额外实车观察，增加了蓝牙音源／控制竞争的可能性；标识本身不能确定 AVRCP PAUSE 的发送者或证明当时存在 A2DP 音频数据。应用的“通过车辆蓝牙播放 CarPlay 音频”开关仅决定是否向 iPhone 提供 CarPlay 音频，关闭它不会主动断开系统蓝牙媒体 profile。车机是蓝牙音频接收端，后续诊断应核对实际 A2DP Sink／HFP Client 能力与状态，不能用常见手机端 A2DP／HEADSET 查询无结果来排除连接。

后续需要把手机播放状态、选中手机的 A2DP 状态／路由变化、原厂音源变化及媒体命令对齐；不直接关闭整车蓝牙，以免破坏配对／通话，也不定时强制恢复播放。
