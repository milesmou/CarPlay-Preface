## 蓝牙自动连接

旧报告仅有 `Phone Bluetooth wake: no matching event recorded`，既没有开关状态，也没有被跳过事件的原因。因此不能断言车机没有发送广播，或断言只是权限问题。

代码原先只监听 ACL_CONNECTED。本轮保留该路径，并补充车机接收端 A2DP sink、AVRCP controller、headset client 的连接状态事件：仅 STATE_CONNECTED 且匹配所选 iPhone 才启动；清单接收器与进程生命周期动态接收器互补，共用 15 秒去重。仍检查用户开关、蓝牙权限与已有会话。明确启动异常时释放本次去重，允许后续事件重试。

报告增加开关、是否已选手机、最近事件类型与固定跳过原因，不记录蓝牙地址。断开事件不会启动连接；开启设置不会伪造一次蓝牙重连事件。动态接收器只在进程存活期间工作；清单广播的交付与后台页面启动仍受系统限制，不能承诺被强行停止的应用自动唤醒。本轮没有证据证明新增事件监听已经解决该车机故障。

验证：`PhoneBluetoothReceiverTest` 在 API 28 / 29 共 8 项通过，覆盖所选手机与开关、三种 profile 状态、跨事件去重、明确启动失败重试和未选手机诊断。未运行全量 CI，未构建或安装新 APK。

## USB 连续失败后的复核

此前仅概括为“USB 网络通路未通”不够准确。正常内核路径在 16:26:41.558 已有邻居 `reachable=1`，16:26:41.565 的指定 usb0 计数显示收到过 Neighbor Solicitation 与 Neighbor Advertisement，且 16:26:41.566 已发送 Neighbor Advertisement。至少邻居发现已双向进行；不能用接管接口之后的原始 OUT=-1 倒推接管前的系统网卡不能收发。

正常路径已有认证、ready IPv6、StartSession 和监听，但无 AirPlay TCP。现有证据仍不能区分手机启动决策、报文参数和系统 TCP 路径处理。没有车机现场访问，本轮不能确认真实连接根因。

本轮确认并修正的诊断问题：

1. 16:27:06 原始诊断强制 claim/select alternate 后，通知有 link down/up；代码却调用 `frameTest.startSessionSent()`，把切换前发送的启动请求当作切换后已发送。现在通过保留的 iAP2 通道重新发 StartSession，只有写入成功才启动测试窗口；写入失败不得启动探针。重发仅发生在正常启动已失败、没有建立会话后的诊断交接，不提供新的 AirPlay 通路。
2. 三次探针均请求 100 ms，却被通用启动前策略截为 20 ms。本轮让认证和新 StartSession 之后的诊断保留请求的 100 ms；正常发送的原 20 ms 策略不变。探针仍最多三次、窗口 15 秒，不把增加等待解释为对 -1 原因的确认。

这些是诊断有效性修正，不能描述为正常 USB CarPlay 已修复；也不要求用户重复运行原逻辑收集第四份相同报告。测试验证发送失败不会启动窗口、成功写入后才启动、诊断超时预算，以及原窗口释放和系统网卡保护；未构建 APK，未做实车验证。
