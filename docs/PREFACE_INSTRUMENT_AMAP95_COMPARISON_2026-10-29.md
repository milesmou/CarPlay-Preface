## 9.5 并非删除了全部扩展协议

JADX 1.5.6 对用户 APK 生成了可搜索源码；命令返回 1，报告 4 个错误，涉及 Base64 编码方法，另有 107 个警告。以下方法已生成可阅读代码，但不将整个反编译结果宣称为无误还原。相对本机 `amap95-decompiled/sources/`：

- `com/autonavi/amapauto/jni/protocol/AndroidProtocolExe.java:1097–1141`：仍存在 `sendExScreenStatus`，按登记的扩展画面类型区分普通扩展与 AIDL Widget；真实扩展状态 0 构造内部状态 200，Widget 则构造 3026。
- `defpackage/ab.java:113–118`：仍将内部 116→协议 200、内部 200→协议 116。不能把普通首帧 200 改名为准备 116，也不能直接重放原厂成功广播。
- `defpackage/v70.java:277–285`：协议 30801 仍接入扩展画面处理；`defpackage/a20.java:112` 起仍按 `PresentationConfig`、实际显示／Surface 及适配器创建扩展画面。
- `com/autonavi/amapauto/jni/MultiScreenNative.java`：画面建立／改变／销毁仍有 JNI 原生调用。仅复制 Java 状态类或回调不能产生真实渲染完成。

因此本轮可定位为：**成功流程所需的原厂仪表准备没有在这次 9.5 运行窗口中完成**。配置、实际画面创建、适配器和原生插件的哪一环最先缺失仍需进一步执行证据，不能仅凭没有状态 116 就认定 9.5 完全不支持所有仪表，或将整个根因归结为一个库文件。

## 能否直接搬模块

327 APK 实际内置 `libInstrumentPannelLarge.so`、`libInstrumentPannelSmall.so` 和对应两个 `libcmb_InstrumentPannel*Package.so`。用户这份 9.5 APK 没有这四个同名文件，但 `defpackage/yw.java:151–152` 仍注册仪表库名；注册表条目不等于插件存在或已经运行。

使用现有 NDK `llvm-readelf --dynamic` 核对，旧版两个仪表库都链接原厂引擎、导航、语音等一组库，其中有 **9 个非系统依赖库名没有打入这份 9.5 APK**，包括 `libGNaviDice.so`、`libARDrive.so`、`libifly_aime_gd.so` 等。进一步比较可正常解析的已打包 ELF 动态符号，大／小仪表库各有 54／45 个 C++ 导入名未在 9.5 导出集合中找到；这只用于判定不能直接混用，不等于实际运行的 linker 报错。外部下载插件、设备预存库和运行时加载没有验证。

所以不能把这四个文件直接塞进 9.5 或 CarPlay 就交付为“已移植”。两条目标需要区别：

1. **让第三方 9.5 自身恢复原车仪表适配**：需补齐匹配 9.5 的设备适配、扩展画面配置和插件。旧 5.x 二进制与新核心接口不匹配，本轮没有形成可安装的修补包。
2. **让 CarPlay 不再依赖高德准备**：当前真实路线、转向映射、SDK 连接和发送已经具备成功证据，后续应独立实现有真实生命周期依据的准备／释放适配。现有仓库规则仍禁止直接调用投屏开关、写系统准备属性、伪造高德事件或扩权授权组件；本轮没有找到可以在这些条件下直接使用的独立准备入口，因而尚不能交付独立移植实现。

移植方向是复用已确认的接口行为并补齐独立准备流程；直接搬入高德地图引擎会继续携带地图生命周期和版本依赖。不能用 CarPlay 主视频首帧冒充原厂扩展地图首帧，也不能通过额外创建虚假画面来通过准备条件。

本轮完成日志、APK、动态依赖及协议对比，更新事实记录；应用行为、设置、权限及版本不变。未运行 Gradle、构建、签名、安装或提交 Git。没有在线 ADB 设备。原始证据及分析见本机 `readiness-summary.json`、`pid-and-map-protocol-summary.json`、`carplay-success-output-summary.json`、`native-compatibility-summary.json` 和 `compare_native_modules.py`。

## 后续：将原厂仪表库放入独立服务

后续用户要求修改后的源码范围见 [独立进程服务](PREFACE_INSTRUMENT_SERVICE_2026-10-29.md)：私有服务和现有 SDK 发送迁移已实现，原厂库完成本地固定哈希导入，但完整引擎初始化未实现、库未默认打包，不能视为原厂仪表库已经独立运行。以下保留提出服务方案时的分析事实。

用户进一步提出将原厂高德仪表库单独做成服务。**独立进程可避免旧 5.x 原生库与 9.5 原生库混用，是可以继续验证的封装方案；它没有自动解决原厂准备状态，当前尚未形成可用服务。** 前文不能直接混用的结论不等于完整旧依赖放在独立进程也必然不可运行。

本次继续读取 ELF 动态依赖与启动导出，得到以下静态事实：

| 检查 | 结果与含义 |
| --- | --- |
| 四个原厂仪表文件的递归 `DT_NEEDED` 依赖 | 包括自身共 **28 个已打包库、91,694,752 字节（约 92 MB）**。只计原生库，不包含 Java、地图／UI 资源、JNI 桥接或额外动态加载插件，不能作为最终 APK 体积估计。 |
| 原厂仪表启动导出 | 大／小库均有 `StartupInstrumentPannelLarge/Small` 和退出导出；未发现这些仪表文件导出 `JNI_OnLoad` 或 `Java_*` 入口。不能直接将它们当成提供导航 setter 的 Java SDK。 |
| 启动函数反汇编 | 两个启动入口均访问 `hsl::MultiScreenService`，最终调用 `GNS_FRAME::CGPackage::startupInUI`，传入 `CGFrameSimulation` 参数。证据是引擎 UI 插件启动流程，尚未还原完整 C++ 参数及对象协议。 |
| 车机实际导航发送 | 仍由安装的 `DimInteraction/INaviInteraction` SDK 和原车服务完成；名称含 Instrument 的高德库不能直接等同于车机车辆信号接口。 |
| 真实准备 | 新建服务进程、成功加载库、Binder 连接和 SDK 连接均不能代替真实准备事件；必须验证引擎初始化、真实画面生命周期和退出失效。 |

以 CarPlay 独立仪表提示为目标，若上述启动和准备验证成功，优先在**主 APK 内设置专用进程的 Service**，由 CarPlay 当前控制器通过私有 Binder 传入真实路线和会话身份。服务进程使用完整同版本依赖，不装入 9.5 进程；保持主包原签名及现有权限检查，不默认增加第三个需手动安装的助手 APK，也不扩大授权组件。专用进程不等于 Android `isolatedProcess` 沙箱，不能依靠更换进程获得额外权限。

服务应只在有效导航会话期间取得资源，并在断开、退出、Binder 死亡和引擎失败时停止输出、释放自身资源；会话替换仍需等待旧清理完成。若服务只封装现有 SDK 发送，准备问题将原样保留；若原厂库必须启动完整地图引擎才能真实准备，就不能把它称为仅需两个小库的轻量服务。

独立加载同版本依赖、数据／资源目录适配、以服务身份连接车机、真实准备的触发与回收，以及不启动原厂地图的冷启动显示，均未运行验证。不能先创建空服务或强置 ready 后当作完成。高德 9.5 自身导航接入此服务属于另一个输入适配目标，本次没有默认扩展到接收其他应用的广播或路线。

新增本机证据为 `standalone-service-dependency-summary.json`、`startup-instrument-small.txt`、`startup-instrument-large.txt`、`standalone-service-findings.json`；原厂输入身份沿用上表，完整依赖清单及原始反汇编仍在忽略目录。本次继续只更新分析与事实索引，未引入运行代码、二进制或构建产物。
